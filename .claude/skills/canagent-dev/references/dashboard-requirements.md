# 대시보드·관측성 요구사항 명세 (사용자 승인 원본: 2026-07-07)

사용자 요구를 구현 가능한 스펙으로 정리한 문서. 대시보드/관측성 작업 시 이 문서가 기준이며, 설계 의도의 과감한 변경은 허용되나 아래 4개 핵심 요구는 반드시 충족한다.

## 핵심 요구 (사용자 원문 기반)

1. **정상 모니터링중 표시가 명확할 것** — 서버가 살아있고 장중 루프가 돌고 있음을 새로고침 없이 알 수 있어야 한다.
2. **점수 상위 종목이 보일 것** — 임계값 미달 종목 포함 Top-N 리더보드.
3. **"어떤 기준에 못미쳐 포착되지 않았는지"가 분명할 것** — 종목별·단계별 탈락 사유.
4. **매매가 왜 안 되는지 분명할 것** — 신호 이후 실행 단계(예수금·보유한도·최소주문)의 차단 사유까지.

## R1. 모니터링 하트비트

- 상태 3단계: `가동 중`(마지막 검사 ≤ 6분) / `지연`(6분 초과, 장중인데 검사 없음 — 경고색) / `장외 대기`(장 시간 외).
  - 현재 boolean(가동/대기)은 "장중인데 죽어있음"을 구분 못 함 — 반드시 stale 판정 추가.
- 표시 항목: 마지막 검사 시각, **다음 검사 카운트다운**, 오늘 검사 횟수, 마지막 검사에서 스캔한 종목 수.
- 갱신: `GET /api/monitor/status`를 프론트 JS가 15~30초 폴링 (SSR 탈피). WebSocket은 과설계 — 폴링으로 충분.
- 워커가 검사 시작/종료 시각·스캔 수를 인스턴스 필드가 아닌 **DB(또는 최소한 status 엔드포인트)에 남겨** 재시작 후에도 이력 확인 가능하게.

## R2. 점수 상위 종목 리더보드

- `AnalysisScoreRepository`에 Top-N 쿼리 추가 (예: `findTop20ByAnalysisDateOrderByTotalScoreDesc`).
- 대시보드 섹션 "오늘의 점수 상위 종목": 종목명/코드, 총점, CANSLIM 점수, 컵 점수, **요소별 분해(C·A·S·L·I·M)**, min-score 대비 상태(통과/미달 배지 + 부족 점수).
- 임계값 미달 종목도 보여야 함 — "왜 아무것도 안 잡히는지"를 보는 게 목적이므로 신호 종목만 필터링하지 말 것.
- 데이터 원천: 야간 `AutoTradingWorker`가 저장하는 `analysis_scores` + 장중 분석 결과.

## R3. 포착 실패(탈락) 사유의 기록과 표시

- **검사 퍼널 카운터**: 매 장중 검사마다 단계별 집계를 기록 —
  `스캔 대상 N → 현재가 조회 실패 a → 보유중 제외 b → 신호 미달(CANSLIM<40 & 컵 없음) c → 총점<min-score d → 신호 s → 주문 성공 t`.
- 현재 IntradayMonitorWorker의 **무로그 silent return 7곳**(architecture-map §4)을 전부 카운터+사유 기록으로 대체한다. 이것이 이번 개선의 핵심.
- 종목별 탈락 사유 저장: `AnalysisScore`에 사유 요약을 남기거나 경량 엔티티(예: `MonitorCheckLog`) 신설. 분석기 사유 텍스트("재무제표 데이터 부족")가 DTO에서 버려지지 않게 영속화.
- 대시보드 표시: 퍼널 요약 바 + 상위 미달 종목의 "부족 요소" (예: "C:0 (재무 데이터 없음), 컵 패턴 없음 → 총점 55/120").

## R4. 실행 차단 사유

- 신호 발생 후 미체결 사유(예수금 부족, 최대 보유 도달, 최소주문 미달, API 주문 실패)를 신호 기록에 남기고 대시보드 신호 테이블에 상태 컬럼으로 표시: `주문 완료 / 예수금 부족 / 한도 도달 / 주문 실패(사유)`.

## R5. 전략 설정 정합성 (구현 시 함께 처리)

- `trading.min-score` 기본값이 워커(120)와 `TradingStrategyService`(60)에서 다름 — 단일 출처로 통일하고, 대시보드에 **현재 유효 임계값**을 표시.
- min-score=120은 재무 데이터가 완비돼도 컵 패턴 없이는 도달 불가(CANSLIM 만점 100). 임계값 자체를 재검토하거나, 데이터 완비율을 함께 표시해 사용자가 판단할 수 있게 할 것.

## 비목표 (과설계 방지)

- WebSocket/SSE, 차트 라이브러리 도입, 프론트 프레임워크 전환 — 하지 않는다. Thymeleaf + 경량 JS 폴링 유지.
- 알림 채널 확장은 별도 요청 시에만.
