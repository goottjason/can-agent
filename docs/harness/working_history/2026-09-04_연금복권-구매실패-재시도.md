# 연금복권(WIN720) 구매 실패 재시도

- 날짜: 2026-09-04
- 등급: 표준 (실결제 경로 — QA + 사용자 승인 게이트)
- 대상: `sidecar/lottery/buy.py`, 복권 스케줄러·구매서비스·사이드카 어댑터

## 1. 증상과 원인

사용자 보고: 이번 주(제330회) 연금복권이 결제되지 않음. 알림 —

> ❌ 복권 구매 실패: WIN720 — 연금 구매 완료 미확인: 당회차 바로구매 예약구매 제330회 … 십만단위 번호를 선택하세요

**원인은 "재시도 없음" 하나가 아니라 셋이었다.**

| # | 결함 | 위치(변경 전) |
|---|------|--------------|
| C1 | 확인창(alert)을 **문구 없이** 수락 → 실패 사유가 통째로 유실. 알림에 찍힌 텍스트는 게임 화면 기본 UI일 뿐 원인을 담고 있지 않다 | `page.on("dialog", lambda d: d.accept())` |
| C2 | `doOrderRequest()` 후 **고정 6초**만 대기, 완료 문구 없으면 즉시 실패 → 사이트가 느린 날 성공을 실패로 오판 | `_win720_interaction` |
| C3 | 실패 = 그 주 구매 포기. 사이드카·Java 어느 층에도 재시도 없음 | `buy_win720`, `LotteryScheduler` |

실제로 무엇이 결제를 막았는지는 C1 때문에 **사후 확정 불가**. 그래서 사유를 남기는 것(C1)을 재시도(C3)와 같은 비중으로 다뤘다.

## 2. 변경 내용

### 사이드카 (`sidecar/lottery/buy.py`)
1. **확인창 문구 캡처** — `dialogs` 리스트에 message를 남기고 수락. 실패 사유에 그대로 실린다.
2. **완료 판정 폴링화** — 고정 6초 → 최대 20초 폴링(`_wait_purchase_done`). 완료 문구 감지 또는 하드스톱 안내창 등장 시 조기 종료.
3. **WIN720 재시도** — 기본 3회(`WIN720_ATTEMPTS` env로 조정), 백오프 5/15/30초, 매 시도 새 브라우저 컨텍스트·새 조(jo).
4. **중복결제 차단(핵심)** — `BUY_NO`·회차를 확보한 뒤 실패한 경우 = 주문이 나갔을 수 있음. 재구매 전에 MY 당첨내역 원장에서 해당 회차 티켓을 확인하고, 있으면 재구매하지 않고 성공으로 복구한다.
   원장 반영 지연을 감안해 **7초 간격 3회 재조회**(`ledger_has_ticket`) 후에만 '미구매'로 단정한다. 브라우저는 1회만 띄우고 재조회만 반복.
   원장 조회 자체가 실패하면 **재시도 금지**(확인 불가 상태에서 재구매하지 않는다).
5. **하드스톱 분류** — 예치금 부족·한도·마감·점검 등은 재시도 무의미하므로 즉시 중단. 판정 대상은 `doOrderRequest()` **이후** 뜬 확인창만(`mark` 인덱스) — 정상 확인창 문구가 키워드와 겹쳐 재시도가 조용히 죽는 것을 막는다.
6. **예치금 선제 확인** — 구매 전 1000원 미만이면 브라우저를 띄우지 않고 즉시 명확한 사유로 실패.
7. 원장 스크래핑을 `_scrape_ledger(page)` / `_with_ledger_page(client, fn)`로 분리 — `check_results`와 `ledger_has_ticket`이 공유(동작 동일).

### Java
8. `LotteryScheduler.retryBuy()` — `lottery.buy-retry-cron` 기본 `0 0 11,15 * * TUE,WED,THU` (KST). `buyWeekly()`는 주차 단위 DB 가드로 **미구매 게임만** 요청하므로 멱등. 연금 판매마감(목 17시경) 전까지만 시도 — 마감 후 구매는 다음 회차가 되어 이번 주 복구가 아니다.
9. `LotteryScheduler.reportUnpurchased()` — `lottery.buy-deadline-cron` 기본 목 15:30. 재시도 창이 끝났는데 미구매가 남으면 최종 통보. 실패 알림을 주 1회로 억제하므로 **결말은 여기서 확실히 알린다.**
10. `LotteryPurchaseService` — `buyWeekly()` `synchronized`, 주 단위 알림 중복 억제(`notifyOnce`). 억제 키는 사유 원문이 아니라 `[:(]` 앞 머리말로 정규화(`failureKey`) — 뒤에 붙는 가변 본문 때문에 억제가 무력화되지 않게.
11. `PythonLotterySidecarAdapter.runProcess` — 출력 읽기를 별도 스레드로 분리. 기존 `readAllBytes()`는 같은 스레드에서 EOF까지 블로킹해 **`waitFor` 타임아웃에 도달하지 못했다** → 멎은 사이드카가 스케줄러 스레드(pool=3)를 영구 점유. 재시도로 실행시간이 길어지면서 실위험이 되어 함께 고쳤다. UTF-8 명시.
12. `sidecar-timeout-sec` 120 → **600** (LotteryConfig + application.yml). 최악 추정 ≈ 470s(3시도 × 50s + 3회 원장확인 × 100s + 백오프 20s).

## 3-1. 후속 수정 — 번호 소진 재선택 (같은 날, 배포 후)

배포 직후 사용자가 실패 원인을 지목했다: **자동으로 뽑힌 번호를 살 수 없는 경우**. 연금복권720+는 조·번호별 발행량이 한정돼 있어 소진된 번호가 나온다. 서버 예치금이 9,000원으로 확인돼 예치금 부족은 아니었다는 점도 이 가설을 뒷받침한다.

**그런데 첫 구현이 이 경로를 정면으로 막고 있었다.** 하드스톱 키워드가 `"마감"`·`"중복"`·`"제한"` 단어 단위여서, "판매 **마감**된 번호입니다" 같은 **번호 단위** 안내가 회차 마감으로 오분류 → 하드스톱 → 다른 번호로 재시도하는 경로가 죽는다.

수정:
1. **번호 단위 사유를 분리**하고 하드스톱보다 **우선**시킨다. `_WIN720_RETRY_SPECIFIC`(이미 판매·매진·소진·수량·다른 번호…)는 항상 재시도. `_WIN720_RETRY_GENERIC`(구매할 수 없·선택할 수 없)는 **하드스톱 단어가 없을 때만** 번호 사유로 본다 — "구매한도 초과로 구매하실 수 없습니다"가 번호 사유로 오인돼 8분을 헛되이 재시도하는 것을 막는다.
2. **하드스톱을 계정·회차 구절로 좁힌다**: 부족·한도·점검·본인확인·정지 + "판매가 마감/판매 종료/회차가 종료". 단독 "마감"·"제한"·"중복"·"종료" 제거.
3. **번호 재선택**: 번호가 확정되지 않으면 브라우저를 다시 띄우지 않고 **같은 페이지에서 다른 조로 최대 3회 재선택**(`_select_numbers`, 조는 `random.sample`로 매번 섞음). 계정·회차 사유면 즉시 중단.

결과 경로: 번호 못 삼 → 같은 페이지 다른 조 3회 → 새 브라우저로 3회 → 화·수·목 크론 6슬롯.

QA PASS(BLOCKER 0). 최악 실행시간 ~470s → ~482s (600s 예산 내). 사이드카 pytest 35 → **38**, Java 270 유지.

## 4. 다음 단계 참조

**미해결·미검증**
- **라이브 미검증**: 재시도·원장 복구 경로는 실제 동행복권 사이트에서 한 번도 돌지 않았다. 원장 반영 지연이 7초×3회(≈20초)로 충분한지, 완료 문구가 실제로 `구매가 완료`인지(변경 전 코드의 가정을 그대로 승계)는 **다음 화요일 실행 로그로만 확인 가능**.
- **330회는 이미 놓쳤다**: 이 변경은 다음 회차부터 적용된다. 330회를 사려면 목 17시 마감 전 수동 구매가 필요.
- **근본 원인 미확정**: C1(사유 유실) 때문에 확정 불가. 다만 배포 후 서버 예치금이 9,000원으로 확인돼 **예치금 부족은 아니다**. 유력 가설은 번호 소진(3-1) 또는 사이트 지연. 다음 실패 시에는 확인창 문구가 알림에 실린다.
- **번호 소진 문구 미확인**: `_WIN720_RETRY_SPECIFIC`/`_WIN720_HARD_STOP` 키워드는 동행복권이 실제로 쓰는 문구를 **본 적 없이 추정**한 것이다. 다음 실패 알림에 실릴 확인창 원문을 보고 키워드를 교정해야 한다.
- **로또(LOTTO645)는 사이드카 재시도 없음** — dhapi HTTP 경로라 중복구매 가드가 없어 의도적으로 제외했다. Java 레벨 재시도(주간 DB 가드)로만 커버된다. 로또도 사이드카 재시도가 필요하면 원장 가드를 먼저 붙여야 한다.

**핵심 결정과 이유**
- 재시도를 **사이드카(3회) + Java(주 6슬롯)** 2층으로 나눈 이유: 사이드카 재시도는 브라우저·타이밍 실패를, Java 재시도는 네트워크 단절·사이트 점검·컨테이너 재시작 같은 긴 장애를 각각 커버한다. Java 층은 DB 가드로 이미 멱등이라 추가 위험이 없다.
- 원장 확인을 "재시도 전 필수 관문"으로 둔 이유: 이 시스템에서 최악의 결함은 실패가 아니라 **중복 결제**다. 확인 불가면 재시도하지 않는 쪽으로 기울였다.
- 마감 후(목 17시 이후) 재시도를 하지 않는 이유: 그때 사면 다음 회차가 되어 이번 주 복구가 아니고, 다음 주 화요일에 또 사서 같은 회차 2장이 된다.

**배포 상태**: 미배포. `deploy.sh`·push는 사용자 승인 필요.
